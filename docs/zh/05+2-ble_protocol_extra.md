# PixLink（常駐）

本文描述 Pixl.js 的 **PixLink**，一個常駐的精簡 BLE 介面。
它獨立於 `05+1-ble_protocol.md` 中基於 Nordic UART Service (NUS) 的檔案傳輸協定，
即使裝置不在檔案傳輸模式下也始終可用。

它提供 **兩個頂層命令**，以及一個僅在控制模式下有效的子命令：

1. 進入正常 BLE 檔案傳輸模式。
2. 進入控制模式，主機傳送 3 個輸入，對應 3 個實體按鈕。
3. 按鈕狀態更新（`0x03`），控制模式的子命令。

## 服務

- 服務名稱：PixLink
- 服務 UUID：`7e400001-b5a3-f393-e0a9-e50e24dcca9e`
- 特徵（寫入 / 無回應寫入）：`7e400002-b5a3-f393-e0a9-e50e24dcca9e`（Control TX）
- 特徵（通知）：`7e400003-b5a3-f393-e0a9-e50e24dcca9e`（Control RX）

PixLink UUID 在 Pixl.js 與 AmiLoop 模式下廣播（可容納於 31 位元組的廣播資料）；
amiibolink 模式下廣播資料已滿，因此該模式不廣播此服務，但連線後服務仍然存在。
進入檔案傳輸或控制模式不會停用它，只會改變目前的活動模式。

所有回應都以通知（notification）的形式由 Control RX（`7e400003`）送出。
主機必須先訂閱該特徵（啟用通知）再送出命令，否則裝置沒有回應的管道，會直接丟棄回應。

## 封包格式

與檔案傳輸協定相同的 4 位元組標頭：

| 欄位 | 型別 | 長度 | 說明 |
| ---- | ---- | ---- | ---- |
| cmd | uint8 | 1 | 命令 id |
| status | uint8 | 1 | 請求固定 0；回應為狀態碼 |
| chunk | uint16 | 2 | 0（無分塊；控制封包單一 ATT 寫入） |
| data | byte | N | 命令相關資料 |

數值型別為無號整數，小端序。不使用分塊傳輸，每個命令都可容納於一次 ATT 寫入。

已知命令的請求必須帶 `status = 0` 與 `chunk = 0`。
若 status 或 chunk 非 0，即為格式錯誤：`0x01` 與 `0x02` 會以狀態 `0x01` 拒絕；
`0x03`（沒有回應）會被直接忽略；未知命令一律以 `0xFF` 回覆。

## 狀態碼

| 代碼 | 說明 |
| ---- | ---- |
| 0x00 | 成功 |
| 0x01 | 一般錯誤（請求格式錯誤，或命令無法排入佇列） |
| 0x02 | 無效的模式切換（例如已在目標模式） |
| 0xFF | 未知命令 |

未知命令會以與請求相同的命令位元組，加上狀態 `0xFF` 回覆。

## 模式與命令對照表

| 目前模式 | 命令 | 動作 | 回應 |
| ---- | ---- | ---- | ---- |
| 閒置 | 0x01 | 啟動 BLE 檔案傳輸應用程式，模式切換為檔案傳輸 | 0x00 |
| 控制 | 0x01 | 結束並重新啟動 BLE 檔案傳輸應用程式（啟動器會先結束目前執行的應用程式，因此該應用程式的介面會重新啟動），模式切換為檔案傳輸 | 0x00 |
| 檔案傳輸 | 0x01 | 不動作，裝置已處於該模式 | 0x02 |
| 閒置 | 0x02 | 模式切換為控制 | 0x00 |
| 檔案傳輸 | 0x02 | 模式切換為控制 | 0x00 |
| 控制 | 0x02 | 不動作，裝置已處於該模式 | 0x02 |
| 控制 | 0x03 | 套用 3 個按鈕狀態，不回應 | 無 |
| 其他模式 | 0x03 | 忽略，不回應 | 無 |

回應為 4 位元組的封包：`{cmd, status, 0x00, 0x00}`，其中 `cmd` 與請求的命令位元組相同。

命令 `0x01` 從閒置或控制模式送出時，會經由應用程式啟動器執行：目前執行的應用程式會先被結束。
若已經處於檔案傳輸模式，該命令會以 `0x02` 拒絕，且不會重新啟動任何應用程式。

## 命令 0x01：進入正常 BLE 檔案傳輸

將裝置切換至正常 BLE 檔案傳輸應用程式（NUS 協定，見 `05+1-ble_protocol.md`）。
檔案傳輸服務沿用既有的連線，裝置不會另外廣播第二個服務，也不會建立第二條連線；
連線關閉後才會恢復廣播。PixLink 仍保持可用以切換模式。

請求：

| 欄位 | 型別 | 長度 | 值 |
| ---- | ---- | ---- | ---- |
| cmd | uint8 | 1 | 0x01 |
| status | uint8 | 1 | 0 |
| chunk | uint16 | 2 | 0 |

回應：

| 欄位 | 型別 | 長度 | 值 |
| ---- | ---- | ---- | ---- |
| cmd | uint8 | 1 | 0x01 |
| status | uint8 | 1 | 成功為 0x00，已在檔案傳輸模式則為 0x02 |
| chunk | uint16 | 2 | 0 |

## 命令 0x02：進入控制模式

將裝置切換至控制模式。在此模式下，主機透過軟體驅動 3 個實體按鈕。
在進入控制模式之前就已被按下的按鈕，仍持有按鈕狀態，並照常送出放開事件，避免介面卡在按住的狀態。
在控制模式期間發生的實體按壓會被完全忽略（按下、放開、長按與連續重複皆被抑制），也不會阻擋虛擬輸入。

若檔案傳輸應用程式正在執行，它仍會繼續執行，改變的只有輸入模式。

請求：

| 欄位 | 型別 | 長度 | 值 |
| ---- | ---- | ---- | ---- |
| cmd | uint8 | 1 | 0x02 |
| status | uint8 | 1 | 0 |
| chunk | uint16 | 2 | 0 |

回應：

| 欄位 | 型別 | 長度 | 值 |
| ---- | ---- | ---- | ---- |
| cmd | uint8 | 1 | 0x02 |
| status | uint8 | 1 | 成功為 0x00，已在控制模式則為 0x02 |
| chunk | uint16 | 2 | 0 |

### 按鈕輸入（僅控制模式）

進入控制模式後，主機在同一 Control TX 特徵上以 cmd `0x03`（控制模式的子命令）
傳送按鈕狀態更新。每次更新包含 3 個位元組，依固定順序對應 3 個實體按鈕：

| 位元組 | 按鈕 | 值 |
| ---- | ---- | ---- |
| 0 | 按鈕 A（左） | 0 = 放開，非 0 = 按下 |
| 1 | 按鈕 B（中） | 0 = 放開，非 0 = 按下 |
| 2 | 按鈕 C（右） | 0 = 放開，非 0 = 按下 |

封包：

| 欄位 | 型別 | 長度 | 說明 |
| ---- | ---- | ---- | ---- |
| cmd | uint8 | 1 | 0x03 |
| status | uint8 | 1 | 0 |
| chunk | uint16 | 2 | 0 |
| btnA | uint8 | 1 | 0 = 放開，非 0 = 按下 |
| btnB | uint8 | 1 | 0 = 放開，非 0 = 按下 |
| btnC | uint8 | 1 | 0 = 放開，非 0 = 按下 |

封包長度必須剛好為 7 位元組。每個按鈕位元組都是布林值：0 表示放開，任何非 0 的值表示按下。
裝置端不做消抖：只有按鈕狀態「變化」時才會產生事件。0 變 1 產生按下事件，1 變 0 產生放開事件，
放開同時也算一次短按，與實體按鈕的行為完全相同。送出相同的數值不會產生任何事件。

若按鈕在進入控制模式之前就已被按下，實體按壓仍持有按鈕狀態：此時虛擬的按下不會再產生一次按下事件，
對應的虛擬放開也不會產生放開或短按。若實體按壓是在控制模式期間發生的，它會被完全忽略，
不會持有按鈕狀態，因此也不會阻擋虛擬的按下。

`0x03` 更新不回應（射後不理），以降低延遲。
非控制模式下傳送 `0x03`，或封包格式錯誤，皆會被忽略且沒有任何回應。

## 退出模式

- 若要離開控制模式，傳送命令 `0x01`（進入檔案傳輸）：裝置會離開控制模式並進入檔案傳輸模式。
  沒有獨立的「退出控制模式」命令；模式切換一律由兩個頂層命令之一發起。重新開機也會把模式重置為閒置。
- 結束檔案傳輸應用程式（例如使用者將它關閉）會把 PixLink 模式重置為閒置。
- 離開控制模式時，仍被虛擬按住的按鈕會送出放開事件（只有放開，沒有短按）。
  若虛擬按下並未送達介面（因為實體按壓已持有該按鈕狀態），則不會送出放開事件。
- 在控制模式之外，實體按鈕的行為不變，包含長按與連續重複。在控制模式期間，所有實體按鈕事件都會被抑制，
  但在進入控制模式之前就已按下的按鈕，其放開事件仍會照常送出。

## 備註

- PixLink 常駐；模式狀態保存於 RAM，重新開機即重置。
- 同一時間應只有一個客戶端驅動控制模式；不仲裁併發寫入。
- 非 0 的值視為按下；如需消抖由主機負責。
- 回應為盡力而為：若裝置的通知佇列已滿，回應可能會被丟棄，因此主機應設定逾時。
